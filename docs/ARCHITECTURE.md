# Architecture

OpenPortsGames is a fully static site: Next.js builds it once and exports plain
HTML/CSS/JS plus `/api/ports.json` as a static JSON file. There is no server,
database, accounts or build-time runtime other than the compiler.

## High-level layout

```
src/
  app/                Routes. Server components that fetch validated data.
  components/         Client UI (catalog, ports, docs, header/footer, theme, i18n).
  content/            The catalog as code: ports/*.ts, hardware, tests, meta.
  lib/
    ports/            Data layer: schemas (zod), registry, queries, API builder.
    i18n/             Dictionaries and the client-side locale store.
    site.ts           Site name, description, URL helpers.
    seo.ts            Per-page metadata helper.
    dates.ts          Date utilities.
scripts/              check-latest-releases (catalog freshness), serve-static.
tests/
  unit/               Vitest — pure utilities and data-layer behavior.
  content/            Vitest — validates the catalog data invariants.
  e2e/                Playwright smoke tests over the static export.
docs/                 Design, data model, policy, methodology, deployment.
```

## Data flow

1. `src/content/ports/*.ts` — plain typed objects (one file per port), plus
   `src/content/hardware`, `src/content/tests`, `src/content/ports/meta.ts`.
2. `src/lib/ports/schema.ts` — zod schemas: `portSchema` (discriminated union
   that excludes `takedown` entries from the public catalog), `hardwareSchema`,
   `testRecordSchema`.
3. `src/lib/ports/index.ts` — parses and exposes `ports`, `hardware`,
   `testRecordsValidated` and query helpers (`getPort`, `getPorts`,
   `getTestsForPort`, `getTestStatuses`, `originalSystemOf`, …).
4. Server components read from that single registry and pass the validated
   objects (serializable only) down to client components. No component or
   page ever reads content files directly.

## Rendering model

- Every route is static (`output: "export"`). Port detail pages are SSG pages
  generated by `generateStaticParams` from the registry.
- The interface is localized client-side: `LocaleScript` bakes a safe default,
  `LocaleProvider` swaps dictionaries, and locale reads go through
  `useSyncExternalStore` so the static HTML never mismatches hydration.
- Theme follows the same pattern (`ThemeScript` + class on `<html>`).

## SEO

- Per-page metadata via `src/lib/seo.ts` (`pageMeta`): title, description,
  canonical, Open Graph, Twitter card.
- `sitemap.xml` (all routes + every port), `robots.txt`, generated
  `opengraph-image`, and JSON-LD structured data (`WebSite` on the home page,
  `VideoGame` on each port detail page).
- `NEXT_PUBLIC_SITE_URL` feeds all canonical URLs; without it, the localhost
  fallback is used.

## Why static

No infrastructure, predictable security, best possible performance, and a
catalog that is versioned in the repository itself. The data layer is
isolated so a future database could replace `content/` without touching
components.
